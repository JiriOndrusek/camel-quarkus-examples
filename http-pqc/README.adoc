= HTTP with Post-Quantum Cryptography (PQC): A Camel Quarkus example
:cq-example-description: An example demonstrating hybrid PQC certificate authentication using Chimera format (RSA + Dilithium3) with the Camel Quarkus platform-http component and BouncyCastle PQC provider.

{cq-description}

TIP: Check the https://camel.apache.org/camel-quarkus/latest/first-steps.html[Camel Quarkus User guide] for prerequisites and other general information.

== Introduction to Post-Quantum Cryptography

Post-Quantum Cryptography (PQC) refers to cryptographic algorithms designed to remain secure against attacks from quantum computers. Traditional cryptographic methods like RSA and ECC could be broken by sufficiently powerful quantum computers using algorithms like Shor's algorithm. PQC algorithms are based on mathematical problems that are believed to be resistant to both classical and quantum computing attacks.

NOTE: For a detailed visual explanation with diagrams showing how client-server communication works with PQC, see link:PQC-EXPLANATION.md[PQC Visual Guide]. It includes ASCII diagrams showing the difference between traditional certificates, our implementation, and Chimera hybrid certificates.

**Simple Example - How Chimera Hybrid Works:**

----
Traditional Certificate (Quantum Vulnerable):
  Certificate
  ├─ Public Key: RSA-2048
  └─ Signature: SHA256withRSA  ⚠️ Quantum can break this

Chimera Hybrid Certificate (Quantum Safe):
  Certificate
  ├─ Primary Public Key: RSA-2048
  ├─ Primary Signature: SHA256withRSA  ✓ Works with old systems
  └─ Extensions (X.509):
      ├─ altPublicKey: Dilithium3
      └─ altSignature: Dilithium3    ✓ Quantum-safe!

Both signatures must be valid = Double protection!
----

This example demonstrates how to:

* Generate Chimera hybrid certificates combining RSA and Dilithium3 signatures
* Validate client certificates requiring both classical and post-quantum signatures
* Automatically generate hybrid PQC keystores at application startup
* Implement quantum-resistant authentication with backward compatibility
* Test certificate validation with both hybrid and RSA-only certificates

=== Why PQC Matters

While large-scale quantum computers capable of breaking current encryption don't exist yet, organizations are adopting PQC now because:

* **Harvest now, decrypt later attacks**: Adversaries can capture encrypted data today and decrypt it when quantum computers become available
* **Long-lived data**: Data that needs to remain confidential for decades requires quantum-resistant protection now
* **Migration time**: Transitioning cryptographic infrastructure takes years, so early adoption is prudent

=== PQC Algorithm Used

This example uses BouncyCastle 1.78.1 for post-quantum cryptography:

* **Dilithium3 (ML-DSA-65 / FIPS 204)**: Module-Lattice-Based Digital Signature Algorithm
  - Security Level: NIST Level 3 (equivalent to AES-192)
  - Use case: Post-quantum digital signatures in hybrid certificates
  - Demonstrated in: Chimera hybrid certificates with RSA + Dilithium3
  - Note: BouncyCastle 1.78.1 uses "Dilithium3" name; ML-DSA names require BC 1.79+

=== Important Limitations on Java 17

**Java 17 does NOT support PQC algorithms in TLS handshakes.** This example uses Chimera hybrid certificates that combine classical RSA with post-quantum Dilithium3 signatures in standard X.509 extensions. The certificate validation happens at the application level, not in the TLS handshake itself.

For full PQC TLS support (hybrid cipher suites like X25519MLKEM768), you need:
* Java 21+ with BouncyCastle JSSE provider, OR
* Java 27+ with native PQC support (JEP 527 target)

This example provides value by showing how to:
* Generate and validate hybrid PQC certificates on Java 17
* Implement application-level PQC authentication
* Build PQC-ready services that can be upgraded to full PQC TLS when Java supports it
* Maintain backward compatibility while adding quantum resistance

== Certificate Generation

Fresh certificates are automatically generated on every application startup by the `SecurityConfiguration` class. These keystores are created in `target/classes/keystores/`:

* `server-hybrid-keystore.p12`: Server certificate with RSA + Dilithium3 signatures
* `server-hybrid-truststore.p12`: Truststore for validating client certificates
* `client-hybrid-keystore.p12`: Client certificate with RSA + Dilithium3 (for successful auth test)
* `client-rsa-only-keystore.p12`: Client certificate with only RSA (for failure test)

NOTE: Keystores are regenerated on every startup with new cryptographic material. This ensures fresh certificates for development and testing.

**Chimera Hybrid Certificate Format:**

Each certificate contains both classical and post-quantum signatures using standard X.509 extensions:

* **Primary**: RSA-2048 public key and SHA256withRSA signature
* **Extension OID 2.5.29.72** (altSubjectPublicKeyInfo): Dilithium3 public key
* **Extension OID 2.5.29.73** (altSignatureAlgorithm): Dilithium3 algorithm identifier
* **Extension OID 2.5.29.74** (altSignatureValue): Dilithium3 signature

Both signatures must be valid for authentication to succeed. This provides quantum resistance while maintaining backward compatibility with standard TLS implementations.

== Architecture Notes

=== BouncyCastle PQC Provider Integration

The `SecurityConfiguration` class registers BouncyCastle as the primary security provider at application startup and generates hybrid PQC keystores:

[source,java]
----
Security.insertProviderAt(new BouncyCastleProvider(), 1);

// Verify Dilithium3 is available
Signature.getInstance("Dilithium3", "BC");
KeyPairGenerator.getInstance("Dilithium3", "BC");

// Generate hybrid PQC keystores if they don't exist
HybridCertificateGenerator.generateServerKeystore();
HybridCertificateGenerator.generateClientHybridKeystore();
HybridCertificateGenerator.generateClientRsaOnlyKeystore();
----

=== Hybrid Certificate Services

The example provides CDI services for hybrid PQC certificate handling:

* **`HybridCertificateGenerator`**: Utility class for generating Chimera hybrid certificates
  - Generates certificates with both RSA-2048 and Dilithium3 signatures
  - Stores PQC signatures in standard X.509 extensions (OIDs 2.5.29.72, 2.5.29.73, 2.5.29.74)
  - Creates keystores in PKCS12 format
  - Supports generating RSA-only certificates for testing failure scenarios

* **`CertificateValidationService`**: Validates hybrid PQC certificates
  - Verifies RSA signature using standard X.509 validation
  - Extracts Dilithium3 public key from extension OID 2.5.29.72
  - Extracts Dilithium3 signature from extension OID 2.5.29.74
  - Both signatures must be valid for overall validation to succeed

* **`HybridCertificateService`**: Loads and provides server certificate information
  - Loads server certificate from generated keystore
  - Provides certificate details for the `/pqc/hybrid` endpoint

=== Why Application-Level Validation?

This example performs hybrid certificate validation at the application level (in the Camel route) rather than in the TLS handshake. This approach is used because:

1. **Java 17 TLS limitations**: Standard TLS stack doesn't understand Chimera extension OIDs
2. **Quarkus/Vert.x coupling**: Framework is tightly coupled to JDK's TLS implementation
3. **Custom validation required**: Both RSA and Dilithium3 signatures must be validated, which requires custom logic

**How it works:**

1. Server presents hybrid certificate (RSA + Dilithium3) during TLS handshake
2. Standard TLS validates the RSA signature (works with any client)
3. Client presents certificate (Quarkus `client-auth = request`)
4. Camel route extracts client certificate and calls `CertificateValidationService`
5. Service validates both RSA and Dilithium3 signatures
6. Request succeeds only if both signatures are valid

This approach provides quantum resistance while maintaining compatibility with standard TLS implementations. When Java 21+ or Java 27+ with native PQC TLS support becomes available, the validation can move to the TLS layer.

=== Keystore Management

**Generated keystores are excluded from version control** via `.gitignore`:

```
# Generated PQC keystores (regenerated on startup)
src/main/resources/keystores/*.p12
```

This ensures:
* Fresh keystores per environment (dev, test, prod)
* No sensitive key material in repository
* Automatic generation on first startup or via script

**Certificate Generation Script:**

The `generate-certs.sh` script provides a convenient way to generate certificates similar to the reference implementation at https://github.com/oscerd/camel-pqc-tls/blob/main/pqc-ssl-context/generate-certs.sh.

Key differences from traditional keytool-based scripts:

* Uses BouncyCastle to support PQC algorithms (keytool doesn't support Dilithium3)
* Generates Chimera hybrid certificates with both RSA and PQC signatures
* Invokes the `HybridCertificateGenerator` main method via Maven exec plugin
* Can be integrated into build/deployment pipelines

To regenerate keystores:
```bash
rm -rf target/classes/keystores/*.p12
./generate-certs.sh
# Or use Maven directly
mvn quarkus:dev  # Auto-generates on startup
```

=== Native Mode Considerations

BouncyCastle PQC classes work in GraalVM native images. Quarkus automatically handles reflection configuration for BouncyCastle. If you encounter native compilation issues with PQC algorithms, check that:

* BouncyCastle dependencies are in scope
* PQC algorithm classes are reachable from application code
* No dynamic class loading is used with PQC operations
