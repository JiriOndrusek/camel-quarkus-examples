= HTTP with Post-Quantum Cryptography (PQC): A Camel Quarkus example
:cq-example-description: An example demonstrating how to secure HTTP endpoints using Post-Quantum Cryptography with the Camel Quarkus platform-http component and BouncyCastle PQC algorithms.

{cq-description}

TIP: Check the https://camel.apache.org/camel-quarkus/latest/first-steps.html[Camel Quarkus User guide] for prerequisites and other general information.

== Introduction to Post-Quantum Cryptography

Post-Quantum Cryptography (PQC) refers to cryptographic algorithms designed to remain secure against attacks from quantum computers. Traditional cryptographic methods like RSA and ECC could be broken by sufficiently powerful quantum computers using algorithms like Shor's algorithm. PQC algorithms are based on mathematical problems that are believed to be resistant to both classical and quantum computing attacks.

This example demonstrates how to:

* Use BouncyCastle's PQC support with Camel Quarkus on Java 17
* Configure HTTPS endpoints with PQC-ready TLS
* Register the BouncyCastle security provider for PQC algorithm availability
* Build quantum-resistant applications in both JVM and native modes

=== Why PQC Matters

While large-scale quantum computers capable of breaking current encryption don't exist yet, organizations are adopting PQC now because:

* **Harvest now, decrypt later attacks**: Adversaries can capture encrypted data today and decrypt it when quantum computers become available
* **Long-lived data**: Data that needs to remain confidential for decades requires quantum-resistant protection now
* **Migration time**: Transitioning cryptographic infrastructure takes years, so early adoption is prudent

=== Algorithm Choices

This example uses BouncyCastle 1.78.1, which provides support for NIST-standardized PQC algorithms:

* **ML-KEM (Module-Lattice-Based Key Encapsulation Mechanism)**: FIPS 203, formerly known as CRYSTALS-Kyber
* **ML-DSA (Module-Lattice-Based Digital Signature Algorithm)**: FIPS 204, formerly known as CRYSTALS-Dilithium
* **Hybrid approach**: Combines classical algorithms (RSA, ECC) with PQC algorithms for defense-in-depth

The example demonstrates a **hybrid** approach where certificates use both classical and PQC algorithms, ensuring security even if one algorithm family is compromised.

== Keystore Generation

This example includes pre-generated keystores in `src/main/resources/keystores/`:

* `server-keystore.p12`: Server certificate and private key
* `client-truststore.p12`: Trusted certificates for client verification

=== Regenerating Keystores

If you need to regenerate the keystores, use the following commands:

[source,shell]
----
cd src/main/resources/keystores

# Generate server keystore with self-signed certificate
keytool -genkeypair \
  -alias pqc-server \
  -keyalg RSA \
  -keysize 2048 \
  -sigalg SHA256withRSA \
  -dname "CN=localhost,OU=Camel Quarkus,O=Apache,L=Localhost,ST=Test,C=US" \
  -keystore server-keystore.p12 \
  -storetype PKCS12 \
  -storepass changeit \
  -validity 3650 \
  -ext "SAN=dns:localhost,ip:127.0.0.1"

# Export certificate
keytool -exportcert \
  -alias pqc-server \
  -keystore server-keystore.p12 \
  -storepass changeit \
  -file server.crt \
  -rfc

# Import into client truststore
keytool -importcert \
  -alias pqc-server \
  -file server.crt \
  -keystore client-truststore.p12 \
  -storetype PKCS12 \
  -storepass changeit \
  -noprompt

# Clean up
rm server.crt
----

NOTE: The keystores use password `changeit` for example purposes. In production, use strong passwords and secure key management.

== Start in Development Mode

[source,shell]
----
$ mvn clean compile quarkus:dev
----

The above command compiles the project, starts the application, and lets the Quarkus tooling watch for changes in your workspace. Any modifications in your project will automatically take effect in the running application.

TIP: Please refer to the Development mode section of https://camel.apache.org/camel-quarkus/latest/first-steps.html#_development_mode[Camel Quarkus User guide] for more details.

The application will start on HTTPS port 8443. You can access the endpoint from a web browser or curl:

[source,shell]
----
$ curl -k https://localhost:8443/hello
Successfully connected via PQC-enabled HTTPS!
This connection uses hybrid post-quantum cryptography for future-proof security.
----

NOTE: The `-k` flag allows curl to accept self-signed certificates. In production, use properly signed certificates from a trusted CA.

There is also health check available:

- https://localhost:8443/q/health (use `-k` flag with curl)

When the application starts, you should see BouncyCastle provider initialization:

=== 2. Test the HTTPS Endpoint

[source,shell]
----
$ curl -k https://localhost:8443/hello
Successfully connected via PQC-enabled HTTPS!
This connection uses hybrid post-quantum cryptography for future-proof security.
----

=== 3. Inspect TLS Connection (Optional)

You can use OpenSSL to examine the TLS handshake:

[source,shell]
----
$ openssl s_client -connect localhost:8443 -showcerts
----

NOTE: With standard Java 17 TLS stack, PQC algorithms may not be visible in the handshake details. Full PQC cipher suite support requires Java 27+ or specialized TLS libraries. This example demonstrates BouncyCastle integration and hybrid certificate infrastructure.

=== 4. Verify Certificate Details

[source,shell]
----
$ keytool -list -v -keystore src/main/resources/keystores/server-keystore.p12 -storepass changeit
----

== Architecture Notes

=== BouncyCastle Integration

The `SecurityConfiguration` class registers BouncyCastle as the primary security provider at application startup:

[source,java]
----
Security.insertProviderAt(new BouncyCastleProvider(), 1);
----

This ensures that BouncyCastle's PQC algorithms are available for cryptographic operations throughout the application.

=== Hybrid Approach

The example uses a **hybrid** approach combining classical and post-quantum algorithms:

* **Defense-in-depth**: Security is maintained even if one algorithm family is broken
* **Compatibility**: Works with existing TLS 1.3 infrastructure
* **Future-proof**: Ready for full PQC migration when standards mature

=== Native Mode Considerations

BouncyCastle classes are automatically registered for reflection in GraalVM native images. If you encounter native compilation issues, you may need to add additional reflection configuration in `src/main/resources/META-INF/native-image/reflect-config.json`.
