= HTTP with Post-Quantum Cryptography (PQC): A Camel Quarkus example
:cq-example-description: An example demonstrating Post-Quantum Cryptography algorithms (ML-DSA signatures and ML-KEM key encapsulation) using the Camel Quarkus platform-http component and BouncyCastle PQC provider.

{cq-description}

TIP: Check the https://camel.apache.org/camel-quarkus/latest/first-steps.html[Camel Quarkus User guide] for prerequisites and other general information.

== Introduction to Post-Quantum Cryptography

Post-Quantum Cryptography (PQC) refers to cryptographic algorithms designed to remain secure against attacks from quantum computers. Traditional cryptographic methods like RSA and ECC could be broken by sufficiently powerful quantum computers using algorithms like Shor's algorithm. PQC algorithms are based on mathematical problems that are believed to be resistant to both classical and quantum computing attacks.

This example demonstrates how to:

* Use BouncyCastle's PQC algorithms with Camel Quarkus on Java 17
* Generate and verify Dilithium3 digital signatures (ML-DSA-65 / FIPS 204)
* Demonstrate NTRU key encapsulation mechanism (NIST PQC finalist)
* Register and verify BouncyCastle PQC provider at application startup
* Build quantum-resistant cryptographic services in both JVM and native modes

=== Why PQC Matters

While large-scale quantum computers capable of breaking current encryption don't exist yet, organizations are adopting PQC now because:

* **Harvest now, decrypt later attacks**: Adversaries can capture encrypted data today and decrypt it when quantum computers become available
* **Long-lived data**: Data that needs to remain confidential for decades requires quantum-resistant protection now
* **Migration time**: Transitioning cryptographic infrastructure takes years, so early adoption is prudent

=== PQC Algorithms Demonstrated

This example uses BouncyCastle 1.78.1, which provides support for NIST PQC algorithms:

* **Dilithium3 (ML-DSA-65 / FIPS 204)**: Module-Lattice-Based Digital Signature Algorithm
  - Security Level: NIST Level 3 (equivalent to AES-192)
  - Use case: Post-quantum digital signatures
  - Demonstrated at: `/pqc/sign` endpoint
  - Note: BouncyCastle 1.78.1 uses "Dilithium3" name; ML-DSA names require BC 1.79+

* **NTRU (NIST PQC Finalist)**: Lattice-based Key Encapsulation Mechanism
  - Security Level: High (lattice-based cryptography)
  - Use case: Quantum-resistant key exchange
  - Demonstrated at: `/pqc/kem` endpoint
  - Note: BouncyCastle 1.78.1 does not include Kyber/ML-KEM KeyPairGenerator support

=== Important Limitations on Java 17

**Java 17 does NOT support PQC algorithms in TLS handshakes.** This example demonstrates PQC algorithms programmatically through HTTP endpoints, not in the HTTPS connection itself. The HTTPS layer uses standard RSA/TLS 1.3.

For full PQC TLS support (hybrid cipher suites like X25519MLKEM768), you need:
* Java 21+ with BouncyCastle JSSE provider, OR
* Java 27+ with native PQC support (JEP 527 target)

This example provides value by showing how to:
* Use NIST-standardized PQC algorithms in application code
* Integrate BouncyCastle PQC provider with Quarkus
* Build PQC-ready services that can be upgraded to full PQC TLS when Java supports it

== Prerequisites

* Java 17 or later
* Maven 3.9.9 or later
* GraalVM (for native mode only)

== HTTPS Configuration

This example uses standard HTTPS (RSA/TLS 1.3) for transport security. The keystores in `src/main/resources/keystores/` contain conventional RSA certificates:

* `server-keystore.p12`: HTTPS server certificate and private key (RSA 2048-bit)
* `client-truststore.p12`: Trusted certificates for client verification

The **Post-Quantum Cryptography is demonstrated in the application logic** at the HTTP endpoints, not in the TLS handshake itself. See the endpoints section below for how to interact with ML-DSA and ML-KEM algorithms.

=== PQC Endpoints

**1. ML-DSA-65 Digital Signature** (`/pqc/sign`)

Generates and verifies a post-quantum digital signature:

[source,shell]
----
$ curl -k https://localhost:8443/pqc/sign
ML-DSA-65 Digital Signature Demonstration
==========================================

Algorithm: ML-DSA-65 (FIPS 204)
Message: "Hello, Post-Quantum World!"
Signature (first 64 chars): iVBORw0KGgoAAAANSUhEUgAAB...
Signature Length: 3366 characters (base64)
Verification: ✓ VALID

Status: Post-quantum signature successfully generated and verified!
----

You can provide a custom message:

[source,shell]
----
$ curl -k -H "message: Custom test message" https://localhost:8443/pqc/sign
----

**2. NTRU Key Encapsulation** (`/pqc/kem`)

Demonstrates post-quantum key encapsulation mechanism:

[source,shell]
----
$ curl -k https://localhost:8443/pqc/kem
NTRU Key Encapsulation Mechanism Demonstration
===============================================

Algorithm: NTRU (NIST PQC Finalist)
Provider: BouncyCastle
...
----

**3. PQC Information** (`/pqc/info`)

Returns information about available PQC algorithms:

[source,shell]
----
$ curl -k https://localhost:8443/pqc/info
----

NOTE: The `-k` flag allows curl to accept self-signed certificates. In production, use properly signed certificates from a trusted CA.

**Health check:**

- https://localhost:8443/q/health (use `-k` flag with curl)

== Architecture Notes

=== BouncyCastle PQC Provider Integration

The `SecurityConfiguration` class registers BouncyCastle as the primary security provider at application startup and verifies that PQC algorithms are available:

[source,java]
----
Security.insertProviderAt(new BouncyCastleProvider(), 1);

// Verify ML-DSA-65 and ML-KEM-768 are available
Signature.getInstance("ML-DSA-65", "BC");
KeyPairGenerator.getInstance("ML-KEM-768", "BC");
----

This ensures that BouncyCastle's PQC algorithms can be used for cryptographic operations throughout the application.

=== PQC Services

The example provides two CDI services that demonstrate NIST-standardized PQC algorithms:

* **`PqcSignatureService`**: Generates and verifies ML-DSA-65 digital signatures
  - Generates keypair at startup using `KeyPairGenerator.getInstance("ML-DSA-65", "BC")`
  - Signs messages using `Signature.getInstance("ML-DSA-65", "BC")`
  - Verifies signatures with the same algorithm

* **`PqcKemService`**: Demonstrates NTRU key encapsulation
  - Generates NTRU keypair for key exchange operations
  - Shows key sizes and security levels
  - Illustrates quantum-resistant key establishment
  - Note: BouncyCastle 1.78.1 does not include Kyber/ML-KEM; NTRU is used as alternative

=== Why Not Full PQC TLS?

Java 17's TLS implementation does not support PQC cipher suites (e.g., `TLS_AES_128_GCM_SHA256` with X25519MLKEM768 key exchange). This limitation exists because:

1. **No PQC cipher suites**: Java 17 TLS stack predates NIST PQC standardization (2024)
2. **Named group limitations**: Hybrid named groups like X25519MLKEM768 require Java 21+ with BouncyCastle JSSE
3. **Certificate extensions**: Chimera-style hybrid certificates need custom trust managers not supported on Java 17 TLS

This example demonstrates PQC algorithms programmatically, preparing your application for full PQC TLS when Java 21+ or Java 27+ becomes available.

=== Native Mode Considerations

BouncyCastle PQC classes work in GraalVM native images. Quarkus automatically handles reflection configuration for BouncyCastle. If you encounter native compilation issues with PQC algorithms, check that:

* BouncyCastle dependencies are in scope
* PQC algorithm classes are reachable from application code
* No dynamic class loading is used with PQC operations
