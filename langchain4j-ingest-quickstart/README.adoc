= LangChain4j Ingest: the easy path

A folder becomes a searchable knowledge base in one line of configuration:

[source,properties]
----
quarkus.camel.langchain4j.ingest.docs.source.directory=data/docs
----

Every file in `data/docs` is read as UTF-8 text (a `parser` such as Tika handles binary formats), split into segments, embedded with a local ONNX model
(no API key, no network) and written into an in-memory vector store. The application only
provides the two beans a knowledge base needs — an `EmbeddingStore` and an `EmbeddingModel` —
and exposes a semantic search endpoint over the result.

No Apache Camel knowledge is required; the routes doing the work are generated from the
configuration.

== Running

[source,shell]
----
mvn clean compile quarkus:dev
----

Then ask a question:

[source,shell]
----
curl "http://localhost:8080/search?q=How%20long%20is%20the%20warranty%3F"
----

The answer segments come back with their similarity score and the document they came from
(`camel_ingest_document_id` — every segment carries citation metadata).

Drop another `.txt` file into `data/docs` while the application runs: it is picked up on the
next poll and becomes searchable within seconds.

== What this example does not do

The extension keeps no record of what it wrote: an edited file re-ingests on top of its old
segments, removing a file removes nothing from the store, and a restart re-ingests the folder
(the in-memory duplicate register is lost with it — a persistent
`source.idempotent-repository` makes restarts free). Replace and delete arrive with the
synchronising engine in a later release. For a consumer-fed pipeline declared in Java, with
deduplication and a RAG chat on top, see the `langchain4j-ingest-s3-builder` example.
